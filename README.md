# found-issues

我（[@sodesu99](https://github.com/sodesu99)）在各种软件、工具、库和系统里**发现过的问题**记录库。

一条发现 = 一个 issue。写清现象、证据、影响、复现，以及我的判断。不做"转述式吐槽"，只放能指到具体位置、能被别人复核的东西。

## 任何人都可以在这里提交自己的发现

这个库**开放 issue 提交**：不需要是协作者，只要有 GitHub 账号，点 [New issue](https://github.com/sodesu99/found-issues/issues/new/choose) 就行。模板会自动带上 `found-by/community` 和 `status/needs-triage` 标签。

没有 GitHub 账号，或者不想公开提的：直接找我（issue 里留言或别的渠道都行）。

## 什么适合放这里

- 软件 bug（能复现的优先）
- 安全问题、隐私问题、权限越界
- 误导性的 API、文案、默认值
- 设计与实现不一致、文档与实际行为不符
- "静默失败"类问题：看起来成了，其实没成

## 什么不适合

- 需要保密的内容（先脱敏；没修的漏洞别贴利用步骤）
- 单纯的"这个软件不好用"（那是偏好，不是问题）
- 编造的、没验证的猜测——**可以发，但必须标明"未验证"**

## 一条合格的发现长什么样

| 栏位 | 要求 |
| --- | --- |
| 现象 | 发生了什么，谁受影响，什么版本 |
| 证据 | 日志 / 截图 / 报错原文 / 时间戳。**原文引用，不转述** |
| 影响 | 最坏会怎样。"难看"和"会被利用"是两个量级，说清楚 |
| 复现 | 最小步骤；做不到就说明是环境相关 |
| 判断 | 你认为的根因；**不确定的部分明确写"不确定"** |

## 标签约定

- 来源：`found-by/me`、`found-by/community`
- 类型：`type/bug`、`type/security`、`type/design`、`type/docs`
- 状态：`status/needs-triage`、`status/confirmed`、`status/disclosed-upstream`

## 披露规矩

1. 先查上游是否已知或已修，避免重复。
2. 未修的安全问题：只写最小必要信息，注明"已私下报告上游"，不贴可直接利用的步骤。
3. 贴日志前删掉 token、cookie、私密路径、个人信息、设备标识。
4. 上游有对应 issue 的，在这里开一条并交叉链接，不重复搬全文。
